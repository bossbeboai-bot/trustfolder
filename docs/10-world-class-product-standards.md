# 10 · World-Class Product Standards

The bar TrustFolder must clear before it ships to a paying customer. Every shipping decision is checked against these 15 standards.

> **Definition of world-class (§15):**  
> Fast to understand. Easy to use. Safe by default. Polished output. Clear boundaries. Boringly reliable.

---

## Why this doc exists

TrustFolder is a premium AI governance evidence product. It is NOT a basic template generator, NOT a compliance dashboard, NOT a ChatGPT wrapper. The standards below define what "premium" means in concrete, checkable terms — so we can spot drift early.

This doc supersedes any conflicting guidance in earlier docs. When in doubt, read this one first.

---

## §1 · Customer Journey Standard

The user journey must feel simple:

```
Website URL → AI scan → short confirmation → PayPal → calm success page → email delivery
```

**The user must never feel like they are filling a legal/compliance government form.**

Concrete rules:
- ≤ 8 confirmation questions in the buying flow (Tier 1). Tier 2 questions only after Tier 2 is enabled.
- No more than 5 minutes total user time before checkout.
- No multi-page wizards with side menus. One screen at a time, plus optional progress indicator.
- No unexpected interstitials between checkout and PayPal.
- No "create an account" before first delivery. Email is the account.

---

## §2 · Magic Moment Standard

The website scan is the product's first wow moment. After URL scan, the user must see a clean prefilled summary:

- Company name
- Product description (1-2 sentences)
- AI feature type (chatbot / content generator / etc.)
- Target users (B2B/B2C, who they serve)
- Likely disclosure needs (Article 50 sections in plain English)
- Any risk warnings (sensitive areas detected)

**If the scan fails, the fallback must feel normal, not broken.**

Failure UX rules:
- Show a friendly message, NOT an error code
- Auto-fall-back to manual confirmation form
- Never show stack traces or HTTP status codes to users
- Never say "the AI is broken" — say "we couldn't read your site, so let's fill it in together"

## §3 · Plain-English Standard

No legal jargon in the public flow. **Technical/legal terms can appear inside the generated pack, not in the early buying flow.**

### Avoid in early flow
- ❌ provider / deployer
- ❌ conformity assessment
- ❌ risk classification
- ❌ ISO control mapping
- ❌ Annex III high-risk
- ❌ Article 50(2) machine-readable marking
- ❌ data subject rights
- ❌ DPIA / DPO

### Use instead
- ✅ "How your AI is used"
- ✅ "Who uses your product"
- ✅ "Where your users are"
- ✅ "What your pack will include"
- ✅ "Needs expert review"
- ✅ "Buyer questions you'll be ready for"
- ✅ "Documents your lawyer will want"

The generated pack uses precise language. The buying flow uses simple language. Two registers, one product.

## §5 · Premium Output Standard

Generated packs must not look like raw ChatGPT output. Every generated document includes ALL of:

1. **Clear title** — the customer's company name + document type
2. **Customer/company context block** — what we know about them, surfaced cleanly
3. **Purpose statement** — one sentence: "This document does X for Y"
4. **Filled content** — no `{{ placeholder }}` left raw, no "TBD" sections
5. **Confidence band** — CLEAR / REVIEW / UNCERTAIN, surfaced as a labeled callout
6. **Review note** — what to bring to your lawyer / who should sign off internally
7. **Practical next steps** — 2-4 concrete actions the customer can take this week
8. **Source notes** — citations to specific Articles, Annexes, ISO clauses
9. **Disclaimer footer** — canonical wording from `01-brand-language-rules.md`

Anti-patterns (auto-fail at QA):
- Empty placeholders (`{{ x }}` left unrendered)
- Unsupported legal conclusions ("you are limited-risk" without "likely")
- Generic ChatGPT-flavored intros ("I hope this helps! Let me know if you have any questions.")
- Marketing language inside legal docs
- Trailing `Generated by AI` watermarks that look unprofessional

## §6 · QA Standard

QA runs against every generation, before delivery. Two layers:

### Layer A — Deterministic checks (auto_fail)
- No blank placeholders (`{{ ... }}` substring)
- No forbidden phrases (canonical list in `01-brand-language-rules.md`)
- No "you are [classification]" patterns without "likely"
- Disclaimer present (must contain "not legal advice" + "qualified")
- All expected files present in the pack manifest
- Markdown is well-formed (no broken table rows, no orphaned headings)

### Layer B — LLM QA (warn or auto_fail)
- Confidence band included for every classification
- Risk warnings present where flagged at scope-check
- Source notes/citations match the document type
- No overconfident legal conclusions
- Output is readable and clean (no run-on Claude rambling, no apology phrases)

### Decision rules
- ANY auto_fail → regenerate the doc once. Second auto_fail → mark `failed_needs_retry`, email customer "we're finishing your pack."
- LLM QA score < 80 → regenerate the entire run with a stricter prompt.
- **False-CLEAR is the worst failure mode.** When uncertain, the classifier biases toward REVIEW. The QA layer enforces this.

## §7 · Out-of-Scope Standard

A world-class product knows when to say no.

### Hard out-of-scope verticals (auto-reject before checkout)
- Healthcare diagnosis / medical devices / clinical decision support
- HR / hiring / employment scoring / performance evaluation
- Credit scoring / lending / underwriting decisions
- Insurance pricing / underwriting decisions
- Biometric identification (vs categorization — categorization is reviewed case-by-case)
- Children's products (anyone < 18 as primary user base)
- Education grading / admissions / student scoring
- Law enforcement / predictive policing / criminal justice
- Critical infrastructure (energy, water, transport management)
- Migration / asylum / border control

### Behavior when detected
1. Do **not** route to PayPal. The checkout button is never shown.
2. Show a calm message: *"This looks like it needs expert review before automated document generation. We will not charge you."*
3. Capture the email with consent for "we expanded coverage" notification.
4. Do not pretend we'll review-and-decide if we won't. Be honest about the decline.

### Soft-out cases (insurance underwriting, legal litigation, government, defense, manufacturing safety)
- Allowed through; flagged for founder review within 24 hours
- Customer sees: "We're confirming a few details and will follow up within 24 hours"
- No charge until founder approves

## §8 · Failure Recovery Standard

No customer should feel abandoned.

### If payment succeeds but generation fails
- Order is saved (the snapshot of customer answers is preserved at create-order time, BEFORE PayPal capture)
- Status becomes `failed_needs_retry`
- Customer sees a calm success/recovery message on `/success/[orderId]`:  
  > *"We hit a small bump and are finishing your pack now. We'll email it shortly. Your order is safe — no action needed."*
- Email goes out: *"We're finishing your pack and will send it shortly."*
- Admin/debug log preserves: full error message, classifier output, generation runs, QA flags
- Retry can be triggered from `pipeline.runPipeline({ order_id, is_retry: true })`

### Refund branch (out-of-scope discovered after payment — rare)
- Auto-refund via PayPal API
- Order moves to `out_of_scope` (terminal)
- Email: refund issued + specialist counsel pointer

### What we do NOT do
- ❌ Show technical error messages to users
- ❌ Tell users to "try again later" without context
- ❌ Lose the order in a queue we can't inspect
- ❌ Make the user re-enter answers after a failure

---

## §9 · Speed Standard

The user should not wait on screen for generation.

After payment:
- Show success page **immediately** (PayPal redirect → `/checkout/return` → `/success/[orderId]`)
- The success page polls `/api/status/[orderId]` lightly (every 4 seconds, stops on terminal states)
- Email delivery happens when the pipeline finishes (5-10 minutes typical)
- Generation runs in the background — never blocking page load

### Targets
- Time-to-first-byte for `/success`: < 1 second
- Status polling cost: ≤ 1 KB per poll
- Pipeline median end-to-end: ≤ 8 minutes (Tier 1) / ≤ 15 minutes (Tier 2)
- Email delivery target: ≤ 12 minutes from payment for 95% of orders

## §10 · Packaging Standard

The final delivery must feel organized, not like a dump of markdown files. Each tier has a specific delivery shape.

### Tier 1 — Lite Readiness Snapshot ($99)
Single short report — no folder structure. Markdown + PDF email attachment, surfaced inline on the success page.

```
TrustFolder-Readiness-Snapshot.md   (single report, ~2-3 pages)
TrustFolder-Readiness-Snapshot.pdf  (same content, PDF)
```

Required sections inside the snapshot:
- Website scan summary
- AI product overview
- Likely transparency/disclosure areas
- Simple readiness result (with confidence band)
- Recommended next steps (which Tier 2/3 pack and why)
- Expert-review / out-of-scope flags
- Disclaimer footer

### Tier 2 — Article 50 Disclosure Pack ($499)
```
TrustFolder-Disclosure-Pack/
├── README.md                       (open this first)
├── disclosures/                    (the Article 50 disclosures, generated conditionally)
│   ├── 01-chatbot-disclosure.md
│   ├── 02-content-labeling.md
│   ├── 03-system-disclosure-page.md
│   ├── 04-deepfake-notice.md       (conditional)
│   ├── 05-emotion-recognition-notice.md (conditional)
│   └── 06-biometric-categorization-notice.md (conditional)
├── placement-guide.md              (where to put each disclosure on your site/product)
├── internal-transparency-summary.md (1-pager for the team)
└── legal-review-note.md            (1-page brief for the customer's lawyer)
```

### Tier 3 — Full AI Governance Evidence Folder ($999)
```
TrustFolder-Pack/
├── README.md                       (open this first)
├── 01-disclosures/                 (Tier 2 disclosures bundled in)
│   ├── 01-chatbot-disclosure.md
│   ├── 02-content-labeling.md
│   └── ...
├── 02-governance/                  (policy, oversight, inventory)
│   ├── 01-ai-system-inventory.md
│   ├── 02-ai-policy.md
│   └── ...
├── 03-evidence/                    (tracker, ISO checklist)
│   ├── 01-iso-42001-checklist.md
│   └── 02-evidence-tracker.md
├── 04-legal-review-handoff/        (lawyer brief, role memo, classification memo)
│   ├── 01-lawyer-handoff.md
│   ├── 02-role-memo.md
│   └── 03-classification-memo.md
└── sources-and-notes.md            (consolidated citations + manifest)
```

## §11 · Visual Standard

Frontend feel:
- Calm
- Premium
- Enterprise-ready
- Not flashy, not crypto-style, not playful, not overdesigned

### Visual rules
| Use | Don't use |
|---|---|
| White / soft (`#f8fafc`) backgrounds | Gradient hero backgrounds |
| Navy / slate text (`#0f172a` / `#1e293b`) | Pure black text |
| Single subtle accent color (one blue, one green for success) | Multi-color rainbow accents |
| Clear progress steps with checkmarks | Animated confetti / particles |
| Generous spacing (≥ 64px section padding) | Dense feature lists with icons |
| 1-2 fonts max (system stack is fine) | Custom display fonts |
| Static screenshots, real product UI | 3D illustrations, abstract shapes |
| Strong trust language above the fold | Discount badges / urgency timers |

The current implementation in `app/app/` is aligned with these rules. Maintain on every new page.

## §13 · Product Value Standard

TrustFolder is not selling blank templates. It is selling an **automated workflow**:

```
website scan → extraction → confirmation → scope check
  → document generation → QA → packaged evidence folder
```

Every output must be more useful than what the customer would get from prompting ChatGPT directly.

### What "more useful than ChatGPT" means
1. **Context-aware:** every doc references the customer's actual company name, product, AI features
2. **Structurally complete:** all 7 (or 19) docs include the same disclaimer, the same confidence-band system, the same citation pattern
3. **Citation-grounded:** every classification cites a specific Article or Annex
4. **Risk-aware:** the customer's specific risk areas (flagged at extraction or scope check) carry through to the generated docs
5. **Lawyer-ready:** the lawyer-handoff doc lets a customer's counsel get up to speed in 15 minutes, not 2 hours

### Anti-patterns
- Generic templates with the company name find-and-replaced — no
- Any doc that reads identically across two different customers — no
- Boilerplate without visible reasoning — no
- Suggestions to "consult a lawyer" without a structured handoff — no

## §14 · Smoke Test Gate Before Phase 3

Before starting Phase 3 (Framer marketing site + brand kit), complete a local smoke test after `npm install`.

### Required test paths (5-tier ladder)

| ID | Path | Pass criteria |
|---|---|---|
| **A** | Tier 0 Free Eligibility Check | URL → scan → 8-question form → web verdict (likely fit / needs review / out of scope). NO documents, NO ZIP, NO PDF. |
| **B** | Tier 1 Snapshot paid PayPal sandbox flow | URL → confirm → PayPal sandbox → success page → emailed `Readiness-Snapshot.md` + `.pdf` arrive. **Blocked until `engine/src/snapshot.ts` is implemented.** |
| **B2** | Tier 2 Disclosure Pack paid PayPal sandbox flow | URL → confirm → PayPal sandbox → success page → ZIP email with the disclosure pack folder arrives |
| **B3** | Tier 3 Full Evidence Folder paid PayPal sandbox flow | URL → confirm → PayPal sandbox → success page → ZIP email with the full governance folder arrives. (Gated to advisor review for production launch, but can run technically in sandbox.) |
| **C** | Website scan failure fallback | Enter unreachable URL → manual fallback shows → user can still proceed |
| **D** | Out-of-scope rejection | Pick `vertical: hr` or `healthcare` → no PayPal button → polite message → email captured (no charge) |
| **E** | Payment success + generation failure recovery | Force a generation error (env hack) → status flips to `failed_needs_retry` → retry email goes out → original answers preserved |
| **F** | Duplicate PayPal webhook idempotency | Replay the same `PAYMENT.CAPTURE.COMPLETED` webhook → no double generation, second call returns `already_processed` |
| **G** | QA failure retry path | Force a forbidden phrase in generation output → QA fails → retry runs once → either passes or marks `failed_needs_retry` |

### Known-pending items before Path B can pass
- [ ] Build `engine/src/snapshot.ts` — generates the single readiness-snapshot Markdown report from extraction + classification data (no full doc generation; one Claude polish pass max)
- [ ] Add Markdown-to-PDF converter (or use Resend's HTML email body for the snapshot to skip PDF for v1)

### Definition of done
- Paths A, B2, B3, C, D, E, F, G all confirmed working OR documented as pending with known fix path.
- Path B is allowed to be marked `pending` until the snapshot generator ships (estimated 2-3 hours of work; see TODO list above).
- Track results in `progress.txt` (or a new `docs/11-smoke-test-log.md` if you want it permanent).
- **Do not start Phase 3 until this is done.**

## §15 · Definition of World-Class

When in doubt, ask:
- Is it **fast to understand?** A new visitor should grasp what TrustFolder does in 10 seconds.
- Is it **easy to use?** A founder with no compliance background should reach checkout without help.
- Is it **safe by default?** No path should expose the customer to false-CLEAR or out-of-scope risks.
- Is it **polished output?** The generated pack should be something a customer is proud to forward to their lawyer.
- Are there **clear boundaries?** The product knows what it is and isn't, and tells the user the same.
- Is it **boringly reliable?** Failures are caught, retries happen, customer is never abandoned.

If the answer to all six is yes, ship it. If not, fix it before launch.
